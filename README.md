# Komari Ping Failure Alerts

为 Komari 1.6.1+ 的 Ping 任务增加故障与恢复通知。插件读取 Komari 的 `ping.loss` 指标，并通过已经配置好的 Komari 通知渠道发送消息；它本身不保存通知渠道密钥。

## 功能

- 连续失败达到阈值后只发送一次故障通知（默认 10 次，可配置 1–1000 次）
- 连续成功达到阈值后发送一次恢复通知（默认 2 次）
- 每个“Ping 任务 × 节点”独立维护状态，支持多任务、多节点
- 成功采样会重置失败计数，短暂丢包不会触发默认告警
- 故障期间去重，不重复刷屏
- 状态保存在 Komari 的插件持久化目录，重启和插件更新后继续去重
- 查询或通知失败不会被当作 Ping 失败，避免把 Komari 自身故障误报为目标故障

## 要求

- Komari `>=1.6.1`
- 至少启用一个 Komari 通知渠道，并允许接收 `PingFailure` / `PingRecovery` 事件
- Ping 任务由节点正常上报；插件仅把明确的 `ping.loss = 1` 计为失败，缺少数据不会被当作失败

## 安装与配置

1. 从仓库最新 Release 下载 `ping-alert.zip`。
2. 在 Komari 后台的插件页面上传并启用，批准“系统 RPC”权限。
3. 在插件配置中选择全部或指定 Ping 任务。
4. 设置连续失败、连续恢复阈值，并确认 Komari 通知渠道已经启用。

插件默认每 30 秒检查一次，可配置 5–300 秒。失败次数按实际探测样本计数；例如每分钟探测一次，默认约持续失败 10 分钟后通知，另加最多一个检查间隔和数据写入延迟。

可选全部或指定任务、全部或指定节点，配置失败/恢复次数（1–1000）、恢复通知开关、采样间隔中断阈值、首次启用是否处理历史、故障/恢复通知模板。

首次启用默认只处理新样本，避免补发过时故障。已有持久化状态会在重启时继续使用。每次查询回溯 10 分钟，可调整 2–14 分钟；只接受原始样本，聚合数据会被拒绝并记录日志。若自定义原始数据保留期更短，请相应缩短回溯窗口。超过连续采样最大间隔会清零连续计数，但不会把无数据误认成恢复。

模板支持 `{{task}}`、`{{task_id}}`、`{{node}}`、`{{uuid}}`、`{{target}}`、`{{count}}`、`{{time}}`、`{{event}}`、`{{message}}`。留空使用默认英文消息；可通过模板写成中文。Bark、Telegram 等渠道在 Komari 自身通知设置中配置。

通知调用失败会保留待发送记录，并指数退避重试（最多间隔 1 小时）。通道部分发送后报错、或进程在发送成功与保存状态之间崩溃，仍可能造成重复消息；Komari 通知接口没有端到端幂等确认，不能保证恰好一次送达。系统关闭通知时核心可能直接返回成功，请先验证渠道能接收自定义事件。

## 防误报与去重说明

- 只有明确失败样本才增加失败次数。
- 任意一次成功都会把尚未触发的失败连续次数清零。
- 触发故障后，后续失败只更新内部状态，不重复通知。
- 恢复需要达到独立阈值，避免目标在成功/失败之间抖动。
- 查询异常、通知异常、任务无节点、无新样本都不会制造故障事件。
- 插件按时间戳记录最后处理的样本，重启后不会重复处理旧记录。

## 开发与测试

```sh
npm ci
npm run typecheck
npm test
npm run check
npm run build
npm run pack
```

打包产物位于 `dist/`，ZIP 根目录包含 `komari-plugin.json`。

## 权限

- `allowSystemRPC`：读取 Ping 任务、节点和 `ping.loss` 指标，并调用 Komari 的统一通知接口。
- `node`：使用受 Komari 限制的 `fs` 模块，把去重状态写入该插件专属持久化目录。

插件不执行外部命令、不监听端口、不注入页面，也不读取插件目录以外的文件。
