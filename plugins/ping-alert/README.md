# Ping 告警与报告

Komari >=1.6.1 插件，按真实 Ping 探测结果判断超时、延迟和丢包率，通过 Komari 已配置的通知渠道发送告警与周期报告。

## 探测次数与延迟判定

- 连续异常探测次数：默认 **10 次**；连续恢复探测次数默认 **2 次**，均可设置 1–1000。
- 超时或负值结果始终视为异常。
- 延迟检测默认关闭，开启后：延迟 **大于**异常阈值也视为异常（默认 200 ms）。
- 恢复要求探测成功，且延迟 **不高于**恢复阈值（默认 150 ms）。
- 两阈值之间的结果既不累计异常，也不累计恢复；会打断正在累计的连续次数。恢复阈值配置过高时会自动限制到异常阈值。
- 同一任务、不同节点独立计数；重复读取同一结果不会重复计数或通知。
- 1 分钟探测一次时，默认 10 次失败约需 10 分钟；插件内部读取新数据的过程不会产生额外 Ping。

检查间隔、回溯设置和手动采样间隔配置已移除。每次启用或重新加载后，仅处理该次启动之后的新探测，不补发历史故障。重启前已告警的故障状态会保留，连续计数和丢包窗口重新累计。内部每 10 秒读取新结果，最长额外延迟约一个读取周期加 Komari 写入延迟；此实现细节不影响探测次数。

超过任务间隔 3 倍或 90 秒（取较大值）没有新样本时，连续计数和窗口自动清零，但不会发送虚假的恢复通知。缺报不等于丢包。只接受原始样本；聚合数据不会用于连续次数判定。

## 丢包率检测

默认关闭，可单独开启，和探测异常告警分别维护故障状态。

- 最近 N 次实际探测构成滚动窗口，默认 **20 次**，可设置 2–1000。
- 收满窗口后，每收到一次新探测，更新一次丢包率。
- 丢包率 = 窗口内失败/超时探测次数 ÷ 窗口实际探测次数 × 100%。
- 高延迟但成功的探测不计为丢包。
- 默认丢包率达到 **20%**，连续 **1 次**更新后告警。
- 默认丢包率不高于 **5%** 且低于告警阈值，连续 **2 次**更新后恢复。
- 窗口大小、告警/恢复百分比、连续超限/恢复探测次数均可配置。

例如最近 20 次探测有 4 次超时，丢包率为 20%。已处于故障时不会重复刷屏。

## 日报、周报、月报、自定义报告

四类报告独立开关，默认全部关闭。报告范围沿用选择的任务和节点。**仅开启探测检测时只报告平均延迟；仅开启丢包率检测时只报告平均丢包率；两项开启时都报告，两项关闭时不生成报告。** 已排队报告如果检测项发生变化会取消，避免发送关闭项的旧内容。

| 报告 | 默认发送计划 | 统计周期 |
| --- | --- | --- |
| 日报 | 每天 09:00 | 上一个完整自然日 |
| 周报 | 周一 09:00 | 上一个完整周一至周一 |
| 月报 | 每月 1 日 09:00 | 上一个完整自然月 |
| 自定义 | 每 6 小时 | 最近 6 小时，可自定义 0.05–8760 小时 |

发送计划为 **Komari 服务端时区** 的 cron（分、时、日、月、周），请在服务器设置中确认时区。插件正文时间默认以 UTC+8 显示，可以调整“通知时间时区”；全局模板中的时间仍由 Komari 控制。

- `30 20 * * *`：每天 20:30。
- `0 */2 * * *`：每两小时整点。
- `0 8 * * 5`：每周五 08:00。
- `@every 2h`：从插件加载后每两小时。
- 自定义统计小时数支持小数：0.5 = 最近 30 分钟。

报告包含每个“任务 × 节点”的平均延迟、平均丢包率和实际探测数，以及总体平均值。使用 Komari `public:getPingMetricStats` 的历史聚合统计，长期数据不依赖原始样本留存。

总体平均延迟按成功样本数加权，平均丢包率按实际探测总数加权，不把各节点百分比直接平均。延迟沿用 Komari 聚合统计口径；核心返回丢包估算标志时会注明“估算”。没有采样显示“无数据”；全丢包时延迟显示“无成功采样”，丢包率可为 100%。

请保留足够的 `ping.latency_ms` 与 `ping.loss` 历史数据：日报至少 1 天，周报至少 7 天，月报至少 31 天，自定义报告至少覆盖所选小时数。核心无法证明历史是否被清理，报告只能统计现存数据，并在正文说明该限制。缺报不会计为丢包。

报告只在配置的计划触发时生成，不补发插件停用期间错过的计划。已触发但查询或发送失败的报告会持久化重试，并保留原统计起止时间。

## 安装和通知渠道

在仓库根 README 所述自用市场源中安装或升级，批准系统 RPC 权限，然后配置所需功能。Bark、Telegram、Webhook 等渠道在 Komari 通知设置中配置，插件不保存渠道密钥。

通知标题/事件名统一为中文：`探测异常`、`探测恢复`、`丢包率异常`、`丢包率恢复`、`探测日报`、`探测周报`、`探测月报`、`探测自定义周期报告`。如果渠道按旧英文事件名筛选，请更新白名单。模板中的 `{{event_code}}` 仍提供旧英文标识，用于自定义兼容。

故障/恢复模板留空使用中文消息，可用占位符：
`{{task}}` `{{task_id}}` `{{node}}` `{{uuid}}` `{{target}}` `{{count}}` `{{latency}}` `{{loss}}` `{{time}}` `{{event}}` `{{message}}`。

## 通知模拟与模板测试（1.2+）

升级后在后台“插件功能 → 通知模拟与模板测试”打开模拟页。选择已开启的探测/丢包通知或周期报告，可填入模拟延迟、丢包率并临时修改故障、恢复、报告模板。

- “预览最终消息”：只生成预览，不发送。
- “发送模拟通知”：明确点击后才通过现有通知渠道发送一次，带有“【模拟】”标记；至少间隔 10 秒，失败不自动重试。
- 测试既不保存临时模板，也不改变真实故障、连续计数、待发队列或报告计划。确认样式后可把模板复制回插件配置。
- 预览包含 Komari 的全局通知模板和 Telegram 的额外标题；客户端字体、自动链接等仍由接收端决定。
- 富文本模板先转为保留段落换行的纯文本，Telegram 再转义 HTML 特殊字符，避免 `<p>` 等不受支持标签导致发送失败。
- 插件正文避免与全局模板重复节点/时间字段；全局模板本身由 Komari 控制，插件不会覆盖它。若希望只保留正文，可自行把全局模板改为 `{{message}}`，这会影响其他系统通知，请谨慎确认。
- 模拟 API 仅允许管理员访问，发送必须是带专用请求头的 JSON POST；浏览器跨站请求会被拒绝。新增 `allowRoutes` 权限需要在升级时确认。

报告模板支持 `{{start}}`、`{{end}}`、`{{latency}}`、`{{loss}}`、`{{nodes}}`、`{{count}}`、`{{event}}`、`{{event_code}}`、`{{message}}`。默认模板按开关过滤；关闭项的占位符为空。自定义模板中的固定文字由你决定，插件不会擅自删除。

## 升级与可靠性

1.0 升级到 1.1 后移除旧检查/回溯配置，原失败与恢复次数、监控范围、模板保留；新增延迟检测、丢包检测和报告默认关闭。旧故障状态会迁移，旧版尚未发送的历史通知保留在原文件中，但不会回溯发送。新版状态保存为插件持久化目录中的 `state-v2.json`。

发送失败会指数退避重试，最长每小时一次，同一故障的异常和恢复按顺序发送。通道部分发送后报错、或发送成功后进程崩溃，仍可能造成重复；核心通知接口不提供端到端幂等确认。请确认 Komari 全局通知已开启，核心在关闭通知时可能直接返回成功。

不执行命令、不监听端口、不注入页面；仅使用系统 RPC 和插件专属存储目录。权限 timeout 提高到 60 秒，以容纳多任务报告。尚未自动升级你正在运行的实例。
